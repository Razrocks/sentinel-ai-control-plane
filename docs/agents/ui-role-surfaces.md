# UI Role Surfaces

How the assistant layer surfaces in the frontend, per role, per page. The shared model: every role sees the same components (ChatPanel global, ContextualAssistant on detail pages); what differs is the *capabilities matrix* — which skills are reachable, which quick actions are offered, and what the agent will or won't do.

## The two assistant components

### ChatPanel — global bottom bar

Lives at the bottom of every page except detail pages. Collapsible. Receives the current page path; entity-scope is page-level, not record-level.

**Existing component:** `frontend/src/components/shared/ChatPanel.tsx`.

**Backed by:** `ChatPanelAgent` via `POST /api/chat`.

**Default visibility:** open on dashboards and list pages; collapsed on settings.

### ContextualAssistant — right rail

Lives in the right rail of detail pages (Change, Incident, Access Request). Receives the entity's id and type as props. Entity-scoped.

**Existing component:** `frontend/src/components/shared/ContextualAssistant.tsx`.

**Backed by:** `ContextualAssistantAgent` via `POST /api/chat` with `context.entityId` set.

**Default visibility:** open.

## Message types — recap

The existing components render 9 message types. The agent layer maps to them as follows:

| Message type | Generated by | Example |
|---|---|---|
| `text` | Default for free-form responses | "The change is in `pending` because two co-approvers have not yet decided." |
| `explanation` | `explain_policy_decision`, `summarize_decision_impact` | Structured rationale with rule name. |
| `recommendation` | `assess_change`, `triage_incident` (when surfacing recommendations) | "Suggest adding a rollback plan because…" |
| `policy_rationale` | `explain_policy_decision` | Cite policy rule + scope + decision. |
| `action_result` | (Backend response, not LLM) — when the user took an action and the agent reports the outcome | "Your approval was recorded. Chain status: 2/3 approved." |
| `guardrail` | When the agent blocks a request | "I cannot approve changes from chat — use the Approvals page." |
| `draft_artifact` | `draft_work_note`, `draft_customer_response`, `draft_approval_packet` | Returns text + a "Save as draft" affordance. |
| `code_snippet` | Rare — shown when the agent quotes a config diff | Read-only. |
| `action_proposal` | Sourced from `propose_bounded_remediation` and similar | "Propose change: restart payment-service" + "Open as draft change" button. |

**v1 rendering simplification:** all responses default to `type='text'`. The infrastructure for the other types is preserved so structured responses can be added skill-by-skill without UI rework.

## Six canonical flows

### Flow 1 — Operator on Dashboard asks "what needs triage"

1. Operator opens Dashboard. ChatPanel is open by default.
2. Clicks quick action "What needs triage right now?".
3. Frontend `chatStream` POST to `/api/chat` with `context.pagePath='/'`.
4. Backend ChatPanelAgent: build T1 + T5 (active freezes) + dashboard-summary slice.
5. Stream response: prose summary of changes pending review, incidents in `new_incident`, access requests pending.
6. No state change. No agent invocation row written for the chat-summary skill (the chat is conversational, not a registered skill v1).

### Flow 2 — Approver opens an Approval inbox item

1. Approver navigates to `/approvals`.
2. Clicks an approval row → modal or detail.
3. ContextualAssistant loads with `entityType='approval'`, `entityId='appr-001'`.
4. Greeting: "I can summarize the decision impact for this approval. Want a one-line read of approve/deny/escalate?"
5. Approver types: "yes". Agent calls `summarize_decision_impact` → renders structured `explanation` message.
6. Approver clicks Approve in main UI. Frontend mutation runs `POST /api/approvals/:id/decide`. Audit event recorded server-side. Agent message: "Your approval was recorded. Chain: 2/3 approved." (action_result message, generated by the backend response handler not the LLM.)

### Flow 3 — Engineer drafts a work note for an incident

1. Engineer on `/incidents/inc-001`. ContextualAssistant open.
2. Engineer types: "draft a work note for the on-call about this".
3. Agent calls `draft_work_note` with incident context.
4. Returns `draft_artifact` message: prose work note + "Copy" + "Save as draft" buttons.
5. Engineer copies, edits in ServiceNow, posts. (v2: "save as draft" persists to incident; v1: copy-only.)

### Flow 4 — Operator asks why a change is blocked

1. Operator on `/changes/chg-002`. ContextualAssistant open.
2. Operator: "why is this blocked?"
3. Agent calls `explain_policy_decision` with the change's `policyDecision` and the rule name.
4. Returns `policy_rationale` message: rule name, scope match, what would unblock.

### Flow 5 — IT triages a new incident

1. IT support on `/incidents/inc-003` (just opened, status=`new_incident`).
2. ContextualAssistant greeting includes the auto-triage output: severity, likely root cause, KB matches.
3. IT asks: "find similar past incidents on this service".
4. Agent calls `triage_incident` again, this time with `mode=similar-search`. (Or v2: a separate `find_related_incidents` skill.)
5. Returns text response with linked incident IDs.

### Flow 6 — Engineer proposes a remediation

1. Engineer on `/incidents/inc-002` (their service). ContextualAssistant open.
2. Engineer: "propose a remediation".
3. Agent calls `propose_bounded_remediation` with incident context.
4. Returns `action_proposal` message: title, description, target service, change-type, "Open as draft change" button.
5. Engineer clicks button → frontend creates a `Change` row via API → enters WF-CHG.
6. New change page opens.

### Flow 7 — Anyone asks "who do I contact about X"

1. User (any role) on any page. ChatPanel open.
2. User types: "who owns customer-data-warehouse" (or "who do I talk to about a problem in customer-data-warehouse").
3. Agent answers inline from T1's Org & Service Catalog — no skill round-trip.
4. Response composes:
   - Primary owner(s) from the service catalog (`User.systemsOwned ∋ 'customer-data-warehouse'`).
   - Their team affiliation.
   - Their role (so user knows whether they can also approve).
   - Their manager (one hop up) for escalation context.
   - A note on whether on-call / paging is available (v1: explicit "paging not surfaced in v1"; v2: live).
5. Follow-up support: if user asks "is C. Davies a change approver?", agent cross-references the approver registry and answers yes/no with scope.

### Flow 8 — Continuity within a session

1. User asks about chg-002 on `/changes`.
2. Navigates to `/incidents/inc-002`. ChatPanel session continues.
3. User: "is this related to what we just discussed?"
4. Agent uses T3 (conversation history) to recall chg-002 was the prior topic, checks `Incident.relatedChanges[]`, answers with the cross-reference.
5. The answer is grounded; if the relationship doesn't exist, agent says so explicitly.

### Flow 9 — Useful chat with state awareness

1. Approver opens dashboard. Asks: "anything I should look at right now".
2. Agent reads the approver's pending-decisions list (small DB query), the active freeze windows (T5), and recent denials in their scope (T4 audit slice).
3. Returns a prioritized response: "Two approvals pending — appr-001 (chg-002, high risk, in active freeze window frz-001 until 04-30) and appr-004 (chg-005, medium, no constraints). Recommend reviewing appr-001 first because the freeze means denial vs delay matters."
4. User clicks through; assistant follows them to the entity page where ContextualAssistant takes over.

## Cross-cutting UI rules

1. **Streaming.** All assistant responses stream token-by-token via SSE. The "send" affordance is disabled while streaming.
2. **Guardrail visibility.** When the agent declines, the response is rendered as a `guardrail` message, visually distinct (existing styling), so the user sees *what* was declined and *why*.
3. **Provenance disclosure.** A subtle badge on each agent response shows "model: claude-sonnet-4 · skill: draft_work_note · 1.4s · ✓" — this maps to the `agent_invocations` row.
4. **Role mismatch.** If the user's role lacks the capability the chat is asking about, the assistant emits a guardrail message: "Your role can read this but cannot act. Escalate via [link]."
5. **Entity-scope assertion.** ContextualAssistant always grounds in the current entity. Asking about a different entity routes to "open that entity" rather than answering across context.
